# mojica MVP Release Plan

## 1. Overview

The mojica MVP will be released as a web application.

For the MVP, the frontend, mojica API, and Glyph Forge API will be deployed independently.

The frontend will be hosted on Cloudflare Pages, while the mojica API and Glyph Forge API will run as Docker containers on Sakura Cloud.

Cloudflare will be used not only to serve the frontend but also to limit excessive requests to the image generation API before they reach the backend.

Advertising will not be introduced in the MVP. Priority will be given to releasing the service and evaluating actual usage.

---

# 2. Release Scope

The following systems will be released as part of the MVP.

| System          | Role                                                    | Runtime Environment   |
| --------------- | ------------------------------------------------------- | --------------------- |
| mojica Web      | User-facing web UI                                      | Cloudflare Pages      |
| mojica API      | Backend API between the web application and Glyph Forge | Sakura Cloud / Docker |
| Glyph Forge API | Text art image generation                               | Sakura Cloud / Docker |

The mobile application is outside the scope of the MVP release.

---

# 4. Cloudflare

## Purpose

The primary purposes of using Cloudflare in the MVP are:

1. Serving the frontend through Cloudflare Pages
2. Limiting excessive requests to the image generation API
3. Reducing the risk of increased backend load and unexpected infrastructure costs caused by excessive traffic

Only the minimum necessary Cloudflare features will be used for the MVP.

---

# 5. Cloudflare Pages

The mojica Web frontend will be deployed to Cloudflare Pages.

The GitHub repository will be integrated with Cloudflare Pages so that changes to the target branch can trigger builds and deployments.

Cloudflare Pages will serve the static files generated by the frontend build.

For the MVP, Cloudflare Pages is responsible for:

- Serving HTML, CSS, and JavaScript
- Serving the SPA
- HTTPS
- Custom domain support
- Deployment through GitHub integration

Cloudflare Pages will not be used as a proxy for the mojica API.

API requests are sent from the user's browser to the mojica API rather than from Cloudflare Pages.

---

# 6. API Rate Limiting with Cloudflare

Because image generation is more resource-intensive than serving static content, `POST /images` will be subject to Cloudflare rate limiting.

```text
Browser
   │
   │ POST /images
   ▼
Cloudflare
   │
   ├── Within limit
   │       │
   │       ▼
   │   mojica API
   │
   └── Limit exceeded
           │
           ▼
       Request rejected
```

If the number of requests within a specified period exceeds the configured limit, Cloudflare rejects the request.

Rejected requests do not reach the mojica API running on Sakura Cloud.

This reduces the following risks caused by sudden increases in image generation requests:

- Increased mojica API load
- Increased Glyph Forge API load
- Excessive server resource consumption
- Unexpected increases in infrastructure usage
- Unexpected increases in infrastructure costs

The exact request limit and time window will be determined based on the processing capacity of the Glyph Forge API, Sakura Cloud pricing, and expected image generation usage.

---

# 7. mojica API

The mojica API will be implemented using ASP.NET Core.

It will run as a Docker container on Sakura Cloud.

Its primary responsibilities are:

- Receiving image generation requests from the web application
- Request validation
- Internationalization (i18n)
- Rate limiting
- Converting HEX colors to RGB
- Calling the Glyph Forge API
- Error handling
- Returning generated images

The mojica API will be used as a public API accessed through Cloudflare.

---

# 8. mojica API Rate Limiting

In addition to Cloudflare rate limiting, the mojica API itself will apply rate limiting.

```text
Browser
   ↓
Cloudflare Rate Limit
   ↓
mojica API Rate Limit
   ↓
Glyph Forge API Rate Limit
```

Cloudflare is responsible for limiting excessive requests before they reach the backend.

The mojica API rate limit serves as a backend-level safeguard to protect both the API itself and the Glyph Forge API.

If the rate limit is exceeded, the API returns `429 Too Many Requests`.

When possible, a `Retry-After` header is also returned.

---

# 9. Glyph Forge API

The Glyph Forge API will run as a Docker container on Sakura Cloud.

It is responsible for image generation.

The mojica Web frontend does not call the Glyph Forge API directly.

The communication flow is:

```text
mojica Web
    ↓
mojica API
    ↓
Glyph Forge API
```

The frontend does not need to be aware of the Glyph Forge API specifications or endpoint structure.

The Glyph Forge API's own rate limiting will also remain enabled.

---

# 10. Docker

The mojica API and Glyph Forge API will be managed as Docker images.

Each application will run in an independent container.

Using Docker reduces differences between local development and production environments and provides a reproducible deployment environment.

---

Frontend:


API:

```text
Browser

```

Backend:

```text
mojica API
   │
   ▼

```

The communication method between the mojica API and Glyph Forge API will be determined based on the network configuration used on Sakura Cloud.

---

# 12. CORS

CORS will be configured on the mojica API.

In production, only the mojica Web origin should generally be allowed.

Local development origins will be allowed separately in the development environment.

A configuration that unconditionally allows all origins will not be used in production.

CORS controls browser-based cross-origin access. It does not replace Cloudflare rate limiting as a mechanism for preventing excessive traffic or protecting the backend.

---

# 13. Environment Variables

Values that differ between environments will not be hard-coded in the source code. They will be managed using environment variables or configuration files.

Examples include:

- Glyph Forge API URL
- Allowed CORS origins
- API timeout
- Rate limit settings
- Runtime environment

If secrets are required, they must not be committed to the Git repository.

---

# 14. Errors and Logging

The mojica API and Glyph Forge API will record the logs necessary for operation and troubleshooting.

Primary logging targets include:

- API errors
- Glyph Forge API request failures
- Timeouts
- Rate limit events
- Unexpected exceptions

Personal information and unnecessary request data should not be logged.

Internal exception information and stack traces must not be returned to users.

---

# 15. Monitoring

For the MVP, the minimum goal is to be able to verify:

- Whether the web application is accessible
- Whether the mojica API is running
- Whether the Glyph Forge API is running
- Whether API errors are occurring continuously
- Whether server resources are becoming exhausted
- Whether Cloudflare rate limiting is being triggered excessively

A sophisticated monitoring platform is not required for the MVP.

---

# 16. Advertising

Advertising will not be introduced in the MVP.

The purpose of the MVP is to release the service and evaluate actual usage. Advertising-based monetization is not a priority.

Introducing advertising may require additional work such as:

- Designing advertising areas in the UI
- Integrating an advertising service
- Creating or updating a privacy policy
- Handling cookies and tracking
- Consent management
- Evaluating performance impact

These concerns are not directly related to mojica's core image generation value and are therefore outside the scope of the MVP.

---

# 17. Advertising After the MVP

Advertising may be reconsidered after actual service usage has been evaluated.

The following factors will be considered:

- Number of accesses
- Number of image generation requests
- Repeat usage
- Server operating costs
- Glyph Forge API processing load

If advertising is introduced, ads should generally be placed where they do not interfere with image generation.

Ads should not be inserted near the image generation button or in the middle of the image generation flow.

---

# 18. Cloudflare Features Outside the MVP Scope

Advanced Cloudflare security features will not be introduced unnecessarily in the MVP.

The following are not mandatory MVP requirements:

- Cloudflare Turnstile
- Advanced bot protection
- Complex WAF rules
- Geographic access restrictions
- Advanced DDoS protection configuration
- Cloudflare Access
- Additional infrastructure for completely blocking direct access to the origin server

These features may be introduced later based on actual traffic and observed issues.

---

# 19. Security Enhancements After the MVP

If excessive traffic, malicious bots, or requests bypassing Cloudflare become actual problems, additional protections will be introduced incrementally.

Potential enhancements include:

1. Restricting direct access to the origin server
2. Cloudflare Turnstile
3. Additional WAF rules
4. Bot protection
5. More detailed access controls

The MVP will not implement all possible protections in advance. Additional measures will be introduced only when necessary.

---

# 21. Release Policy

For the MVP, priority will be given to releasing a usable service rather than overengineering security and operational features.

The basic MVP architecture is:

```text
Browser
   │
   ├── Web
   │     ↓
   │   Cloudflare Pages
   │
   └── POST /images
          ↓
       Cloudflare
       Rate Limit
          ↓
       mojica API
       Rate Limit
          ↓
       Glyph Forge API
       Rate Limit
```

At release, the following core mojica flow must work reliably:

```text
Web
↓
Image Generation
↓
Automatic Download
```

Advertising, the mobile application, image previews, login, storage, direct social media sharing, and advanced Cloudflare security measures are not release requirements for the MVP.
